## Styling (read before touching styles)

**What to build towards is "Visual direction" in `docs/ANALYZER_REDESIGN_PLAN.md`.** This section covers the mechanics of styling.

**Tailwind is the only stylesheet.** `App.css`, the pre-redesign stylesheet (2,062 lines), was deleted on 2026-09-30: from 2026-09-28 it sat in a `legacy` cascade layer that lost to every Tailwind class, and by the end no class the app used was styled by it alone (checked against the built CSS). `src/index.css` holds Tailwind's directives and the few site-wide rules: the font, phone density, the surfaces, keyboard focus, the Z pill's breathing, and the scrollbars (thin; a row that scrolls sideways hides its bar), the last two carried over from `App.css`.

**The look lives in `tailwind.config.js`** (App.css's "modern redesign layer" re-skinned the app by redefining Tailwind's own class names; its values became theme entries on 2026-09-28):
  - radii (`rounded-lg/xl/2xl` = 0.875/1.125/1.5rem)
  - soft `shadow-lg/xl/2xl`
  - the navy surfaces (`bg-gray-800` `#1e2434`, `bg-gray-700` `#2b3245`)
  - the shell palette (`shell-panel` `#1a2031`, `shell-pop` `#222a3b`, `shell-track` `#262e40`, `shell-fill` `#56627a`, `shell-inset` `#121725`). **A table row's opened detail sits on `.surface-inset`** (index.css), a shade darker than the panel so its start and end show (the league, 2026-09-30; darker because popovers are the only raised surface): `StatTable`'s `renderExpanded`, the Builds table's and the Match page's `CharacterDetail`. Parts that must blend into what is behind them (a tile grid's cells, a hollow dot, a cut-out border) paint `var(--surface)` (`bg-[var(--surface)]`, `border-[color:var(--surface)]`), the panel colour by default and the inset one inside a detail; never `bg-shell-panel` for that. **Every page's panel is `bg-shell-panel`** with `border-gray-700`, `rounded-[10px]`, so the site reads as one surface. Menus and tooltips sit on `shell-pop`, bars and rings use `shell-track`, and muted text is slate (`text-slate-400`, `-500`), not gray. `bg-gray-800` is the chip colour, not a panel colour.
  - the faint hairline `border-gray-700` (slate at 18%; its alpha is scaled, so `border-gray-700/60` is still fainter, not brighter)
  - display letter-spacing on `text-2xl`–`4xl`
  - the page column, `max-w-page` (1352px), set as `px-4 sm:px-6` outside and `max-w-page mx-auto` inside by the tab row, the scope bar and App's page wrapper, so all three edges line up. It is the shell demo's 1400px column with its 24px gutter (16px on a phone). It replaced a fluid `max-w-7xl` up to 1760px, which spread a table row too wide to read across on a big monitor.

  **Restyle by changing those values, or the classes in components.**
- **The font is the system UI font**, set on `body` in `src/index.css`: Segoe UI on Windows, Roboto on Android, San Francisco on Apple, as the shell demo and the website render. Inter from Google Fonts was dropped on 2026-09-28. Form controls inherit it (preflight does that now; before, buttons rendered in Arial).

It is carried over from `App.css`'s phone pass and is deliberate; delete it in one go if the restyle moves to per-component `sm:` classes. The phone pass's other rule, collapsing every 3–5 column grid to two, was not carried over: grids say `grid-cols-2 sm:grid-cols-N` themselves.

The switch to Tailwind-first, then deleting `App.css` and turning preflight on (2026-09-30), were checked with it across every view at 1280px and 390px. Run it before merging any sweeping style change: screenshots miss small shifts, and computed styles cannot judge a layout.

## The compact match corpus (`public/br-aggregates/`)

This is how match data reaches the client. **Do not add code that fetches `BR_Data/` files in bulk** — that is the pattern Phase 1.5 removed.

- `scripts/generate-br-aggregates.js` (prebuild, after `generate-br-data-tags.js`; also `npm run build-aggregates`) writes 15 shards — one per `BR_Data/<Top>/<Sub>` folder — plus `index.json`. 2,497 matches, 68.5 MB → 14.6 MB; the Season 0 shard is 1.17 MB raw / ~101 KB gzipped.
- **Shards keep the original match JSON shape** (`TeamBattleResults.battleResult.characterRecord`), with every field no consumer reads stripped out. That is deliberate: `statCalculations.js` and `utils/aggregation/*` consume a shard **unchanged**. `runBlastCount` is pre-summed into a synthetic dict whose keys still satisfy `extractStats`' `includes()` checks, and `attackHitCount` (~230 per-move codes) is replaced by `battleCount.styleHits` — rush / heavy / ki-blast hits, classified by the shared `src/utils/actionCodes.js` that `extractStats` also applies to raw files. The corpus is version 2 (`CORPUS_VERSION` in the generator, `EXPECTED_CORPUS_VERSION` in `src/utils/corpusLoader.js` — bump both together).
- **If you make anything read a new raw field, add it to the keep-lists in the generator**, or it will silently read `undefined` from a shard. Then re-run `npm run verify-aggregates` (`scripts/verify-br-aggregates.mjs`): it compares raw vs compact field-by-field and runs the real `extractStats()` over both sides for all 2,497 matches / 11,914 character entries. It currently passes; treat a failure as a blocker, since a dropped field corrupts published statistics rather than crashing.
- `src/utils/corpusLoader.js` (`loadMatches`) does the client-side loading, falling back to per-file fetches if the corpus is missing, version-mismatched, or lacks a requested match. Single-match navigation (`handleNavigateToMatch`) still fetches the raw file from `public/BR_Data/` — one request, full fidelity.
- **What loads is the scope, a TAG filter in the URL.** `shell/useScope.js` reads it and turns it into match paths through `public/br-data-tags.json`, with no match fetches. `shell/useScopedMatches.js` hands those paths to `loadMatches`. `defaultScope()` gives a scope-less league URL `matchType: Season` plus the newest season with league matches. Tags are visible and self-describing, so a viewer sees at a glance that the data is scoped and how; a silently pre-selected folder looks like the whole dataset. **Do not reintroduce folder pre-selection.**
- **Nothing may load before the scope is final.** `useScope` reports `ready` only once the tag index is in and the URL has a scope, the default having been written in if needed. `paths` stays `null` until then, and `useScopedMatches` loads nothing for `null`. Without that gate the first render would load all ~2,500 matches and pull every shard, undoing Phase 1.5. (The old file tree needed the same gate, through a three-state `tagFilterPaths`.)

## `BR_Data/` and the tagging pipeline

`BR_Data/` is organized `Seasons/`, `Events/`, `Tests/`, each further split into subfolders (team/event names). Files land here via the Submit→Admin PR pipeline documented in root `CLAUDE.md`. On every build, `prebuild` (in `package.json`) runs, **in order**:
1. `scripts/autoTagMatches.js` — auto-tags each match file with `seasonNumber`, `seasonPhase`, `team`, `matchType`, `difficulty`, `matchSize` based on its path/content.
2. `scripts/generate-br-data-structure.js` — builds `public/br-data-structure.json`, which only the deleted file tree read (see above).
3. `scripts/generate-br-data-tags.js` — builds the tag index (`public/br-data-tags.json`) that the scope bar filters against (`src/shell/scopeModel.js`).
4. `scripts/generate-br-aggregates.js` — builds the compact match corpus in `public/br-aggregates/` (see above). Then `scripts/generate-recent-uploads.mjs` writes `public/br-recent-uploads.json`, Home's newest test and event uploads, dated from git (see "The newest uploads").
5. `scripts/verify-character-slugs.mjs` — guards the character URL scheme (see "Character URLs are name slugs" below). **Fails the build** on a slug collision. `scripts/verify-match-slugs.mjs` does the same for match links (see "The Matches list and the Match page").
6. `scripts/verify-portraits.mjs` — warns (never fails) about any character in `characters.csv` without a portrait in `public/portraits/` or its 192px cut in `public/portraits/192/` (see "The Characters and Home pages").
7. `scripts/verify-transformations.mjs` — **fails the build** if the transformation rules break (checked on made-up matches), and warns about form changes the match files record that `referencedata/transformations.json` does not list (see "Transformations" below).

If match data looks stale/missing in the UI after adding files directly (rather than through a PR), re-run `npm run dev` (which triggers Vite) or manually run these three scripts — they don't run automatically on file save, only on build/prebuild.

Separately, `scripts/fix-json-encoding.js` (`npm run fix-json`) and `scripts/watch-br-data.js` handle encoding issues (UTF-16 LE / UTF-8 BOM) in submitted JSON — this also runs in CI (`.github/workflows/deploy.yml` and `.github/workflows/validate-json.yml`, see root `CLAUDE.md`). `scripts/br-data-api-server.js` and `scripts/generateCapsuleMetadata.js`/`src/config/capsuleMetadata.json` support local tooling — check their headers before assuming they run in the build.

## Character URLs are name slugs (read before building the Character page)

Characters are addressed in URLs by a slug of their name, **not** by the internal CSV key: `/analyzer/characters/android-13`, not `/analyzer/characters/0620_00`. Deep links get shared in Discord, and `0620_00` (which is Android 13) tells the reader nothing.

- **`src/utils/characterSlug.js`** owns this. `buildCharacterSlugIndex(csvText)` returns `{ idToName, idToSlug, slugToId, collisions }`; `characterUrlKey(id, index)` gives the URL form; `resolveCharacterParam(param, index)` turns a URL param back into an id.
- **Raw ids still resolve, permanently.** This is not redundancy — a newly released character can appear in submitted match data *before* `referencedata/characters.csv` gains a row, and with no name there is no slug. The id route keeps that character reachable, displaying the raw key until the CSV catches up. It also protects links shared before any future rename.
- **The two namespaces provably cannot collide**: every id matches `CHARACTER_ID_PATTERN` (`^\d{4}_\d{2}$`) and no character name contains an underscore, so the dispatch is one regex test rather than a guess.
- **`npm run verify-slugs`** (`scripts/verify-character-slugs.mjs`, in `prebuild`) asserts slug uniqueness, namespace separation and a lossless `id -> slug -> id` round trip, and **fails the build** on a violation. All 241 characters currently pass with zero collisions. **Do not change `slugifyCharacterName()` without re-running it** — altering the algorithm silently rots every link already shared. A character in match data but missing from the CSV is a warning, not a failure.
- `src/routes.js` stays a pure path builder; `ROUTES.character()` takes the URL key, not an id. Phase 3 should **redirect a raw-id URL to its slug** so the canonical form lands in the address bar.
- Two related gotchas: `statCalculations.js:parseCharacterCSV` splits on the *first* comma (harmless — it only reads the id — but it is why slug parsing does not reuse it), and **47 named characters never appear in the corpus**, so build a `/characters` index from match data, not from the CSV, or it will list dead pages.

## `filterAggregatedData` (the extracted leaderboard filter)

`src/utils/aggregation/filterAggregated.js` filters and sorts the aggregated per-character rows. It was a 695-line `useMemo` inlined in `App.jsx`; the body was moved **verbatim** in Phase 3, so it carries the original behaviour exactly, quirks included.

- **Option defaults mirror `App.jsx`'s `useState` initial values**, not some other idea of "unfiltered" — `minMatches: 1`, `maxMatches: 999`, `sortBy: 'combatScore'`, and `performanceFilters` listing all five levels. The block skips the performance filter entirely unless between 1 and 4 levels are selected, so passing all five is what "off" means.
- Valid `sortBy` values are `combatScore`, `totalDamage`, `avgDamage`, `dps`, `efficiency`, `matches`, `name`. Anything else silently falls back to combat score.
- **`npm run verify-filters`** (`scripts/verify-filter-aggregated.mjs`) runs it over a real corpus shard: sorting in both directions for every key, the match-count window, character selection, purity (it must not mutate its input — the page calls it on every render), and junk input. It is **not** in `prebuild` because it aggregates a real shard and is slower than the other verifiers; run it when you change this function.
- It needs `node --import ./scripts/json-import-hook.mjs` because the aggregation modules `import` a `.json` file the way Vite allows but plain Node does not. The npm script already passes it.
- **A build is `buildKey()` in `src/utils/buildKey.js`** — the exact capsule set plus the AI strategy — and every build table, build filter and aggregation grouping uses it (it had been written out by hand in six places). Its `buildCode()` makes the short code for `?build=` links; a code is always resolved against one character's own builds with `findBuildByCode()`, never globally. `verify-character-page` checks that no two builds of one character share a code across every real build.

**The five level strings are a contract.** `getPerformanceLevel` (`src/utils/performanceLevel.js`) returns exactly one of `excellent`, `good`, `average`, `below-average`, `poor`, and three groups of code key off them: the badge `switch`es and style maps in `App.jsx`, and the leaderboard's performance-filter chips. **Renaming one means updating every consumer.**

They disagreed until 2026-09-26: the filter UI stored the fourth level as `'below'` while the function returned `'below-average'`, so **19.8% of character rows (202 of 1,018 across all 15 shards) silently vanished as soon as a user deselected any performance level.** Fixed by moving the UI onto `'below-average'` — the function was right and had five consumers agreeing with it, the filter had one. `verify-filters` now asserts that the five levels **partition** the whole view, so no row is unreachable; that check is what catches this class of bug, and it is why a level rename cannot regress silently again.

## Performance scoring and tiers

**Tiers are Z/S/A/B/C (Z highest), absolute, and frozen at build time.** `scripts/generate-performance-bands.mjs` runs in `prebuild` and writes `src/config/performance-bands.json`, which is **committed on purpose** — a recalibration should appear as a reviewable diff, not drift silently between deploys. Basis: a rolling window of the last 2 seasons, Ultra difficulty only, all match types, no minimum match count. Read that script's header before changing any of those rules; each one was chosen against measured data.

Two modules, split for a reason: **`src/utils/tierScale.js`** holds the scale and imports nothing, so the generator can read it before its own output file exists; **`src/utils/performanceTier.js`** adds the generated cutoffs and `tierForScore()`. Merging them reintroduces a bootstrap cycle where the build cannot run on a clean checkout.

`src/components/TierPlate.jsx` renders the tier. The artwork is an SVG string built by `src/utils/tierPlateSvg.js`, which also exports `tierPillColors()` so the score pill is tinted from the **same** palette and cannot drift from the plate. **Never pass TierPlate a reference population** — that is the bug it was built to replace. For "how does this stat compare to what is on screen", `PerformanceIndicator`'s relative comparison is still correct.

Three plate states exist and must stay distinguishable: normal, **provisional** (thin sample, stays in colour), and **deselected** (a filter switched off, fully greyscale). They fold into the SVG's single `style` attribute — emitting a second `style=` is silently dropped by the HTML parser, which once left deselected plates in colour.

**The score pill is one component, and its colour is absolute.** `src/components/stats/PerformanceScoreBadge.jsx` renders every "Score: 105" in the app, tinted by `tierForScore` + `tierPillColors` — the same palette as the plate. It used to take an `allScores` prop and colour the score **relative to whatever else was on screen**, so the same character scoring 64 was green in one panel and orange in another, and a pill inside a 2-character match was graded against a single opponent. **Do not reintroduce `allScores`**; for "how does this stat compare to what is on screen", `PerformanceIndicator` is the right component and its relative colouring is still correct. Removing it made `allMatchScores`, `allCharScores` and `combatPerformanceScores` in `App.jsx` dead, along with a third hand-rolled copy of the pill; all are gone.

The leaderboard filter is **tier toggle buttons plus a two-thumb score range** (`src/components/RangeSlider.jsx`), combined with AND. Cutoff numbers are deliberately not shown in the UI; a tooltip explains the scale instead.

Z is the top tier, ahead of S — the Dragon Ball convention, not the generic S-at-the-top. Z keeps a blue slab with a red letter as the Dragon Ball Z mark; S→C follow the loot-rarity ramp (purple, gold, blue, grey). Red and blue-to-red slabs for Z were both tried and rejected — with a red letter there is too little separating the glyph from its own floor at small sizes. **Z's red is crimson (`#ff8fa0` / `#c8102e`, hue ~350°), not orange-red** — the earlier pair sat at ~8–20° and read as bronze at pill size, a warm metal rather than a top-tier mark. **The Z score pill is the one exception to "pill = tint of the plate"**: a dark crimson-black fill (`#2a1418`), a bright crimson ring (`#e0284a`) and a halo that slowly breathes, chosen after four rounds of side-by-side demos (flat, sheen, gold, embers, smouldering border, flame). `tierPillColors('Z')` returns the fill, ring and a resting glow; the breathing lives in `src/index.css` as `.szl-tier-pill-z`, applied via `tierPillClass(tier)`. **Every site that uses `tierPillColors()` must also use `tierPillClass()`**, or Z quietly stops breathing there; `smoke-character-page` checks the badge. Reduced motion keeps the resting glow. Each tier's `letter` pair does three jobs at once: the plate glyph's gradient, the dark-theme pill's text colour (the light one) and its border and background tint (the deep one), so judge any change on the plate **and** the pill, at real sizes. **The pill writes in the tier's light letter colour on a tint of the deep one** (`tierPillColors(tier)`; light mode, removed, needed the deep plate colour, since the light letters measured 1.0–1.1:1 on white). `smoke-character-page` measures WCAG text contrast of every tier's pill against its own tinted background and fails below 4.5:1 — the older "distinct colour per tier" check passed the whole time light mode was broken.



**`src/utils/performanceScore.js` owns the damage-efficiency term.** Efficiency is damage dealt over damage taken, carries 25% of the score weight un-normalised, and is therefore unbounded. The codebase had **three different answers** for "what if nothing was taken?" — return raw damage (mixing units, a five-figure number where a single-digit ratio belongs), return a `999` sentinel, or return `avgDamage/1000`. All three could inflate a score into the hundreds of thousands on a narrow selection. `combatEfficiency(dealt, taken)` replaces all of them with one clamp at `EFFICIENCY_CAP = 5`, about 3x the highest ratio ever observed in league play.

It is a guard rail, **not** a rebalancing: on S0 in-season data real ratios run 0.26–1.73 (median 1.00), and 593 character/team entries across four corpus slices are identical before and after the change. **If the cap starts binding on real data, that is a signal worth investigating, not a number to raise.**

**Performance levels must never be measured against the filtered list.** `App.jsx`'s `performanceReference` memo is the population a character's level and stat bars are compared against. The rule: filters that change *which matches count* (team, AI strategy, map, build filters) define the field because they genuinely change each character's stats; filters that only change *what you are looking at* (performance level, character selection, the match-count window) must not. Measuring against the post-filter list made the levels self-referential — deselecting "Excellent" re-ranked whoever remained, so a character turned green without their score changing.

**`PERFORMANCE_LEVELS` in `performanceLevel.js` is the single source of the level names.** They are a contract shared by the badge switches, the style maps and the filter, and they drifted once already.

Phase 3 replaces all of this with **absolute Z/A/B/C/D cutoffs** calibrated from a rolling last-2-seasons, Ultra-only window — see `docs/ANALYZER_REDESIGN_PLAN.md` "Performance tiers". At that point no reference population is needed at all. Note the score formula is still **duplicated across ~15 sites in 8 files**; consolidating it is outstanding.

## The Character page's league reference (`src/config/style-baseline.json`)

Every rank and "League" number on the Character page Overview (`#12/126`, the league median on a tile, a style's rank) is measured against a **frozen** reference, not against whatever is filtered on screen, for the same reason the tier cutoffs are frozen: a rank that moves when a filter changes is not a rank.

- **Built by `scripts/generate-style-baseline.mjs`** (in prebuild, after the tier bands; `npm run build-style-baseline`) over the **same window as the tier cutoffs**, `scripts/calibration-basis.mjs`, which both generators share: last two seasons, Ultra only. The pool is characters with 5+ appearances (126 today). It stores every pooled character's value per figure, sorted (a rank needs the whole distribution), plus the medians and 95th percentiles the page shows. Committed; rewritten only when the reference actually changes.
- **`src/utils/characterOverview.js` computes a character's figures** from its per-match rows, and the generator runs that **same code** over the whole pool, so a character and the league are measured identically. `overviewFromMatches(matches)` works on all of a character's matches or on one build's (the build filter), and `placeOverview(overview, baseline)` gives `{ pct, rank, pool }`. A single build is ranked against the same reference: where it would place among the characters.
- **Values are rounded to 4 decimals on both sides** (`round4`) before a rank is taken, so a character is never ranked against a rounded copy of itself that sorts a hair below it.
- **`perMatch` is the Match page's reference** (2026-09-29): every single performance in the same window (any character, battle time > 0; 5,778 today) as 21 quantiles per figure, for damage dealt and taken, efficiency, damage per second, battle time, ki blasts and each skill. `src/utils/matchReference.js` defines the figures (`MATCH_METRICS`) for both the generator and the page, and places a value (`placeInQuantiles`, `placeMatch`). **One match is placed among single matches, never among characters' averages**: an average is far less spread out, so a match ranked against averages would look extreme. Its "League" is the typical match (median damage 38,517), which is close to, but not, the Overview's typical character.
- **Fusions: one rule everywhere, set by the league (2026-09-29).** From the moment a character fuses with a teammate, everything it does is split half and half between it and that partner, in every per-character figure: the leaderboard, the Character page, the team figures and roster, positions and the Match page. **Per-form figures are the one exception**, also the league's call: a fused form's own column or row (the Match page's forms, the Character page's Transformations tab) shows the fusion's whole output, which reads truer to how the match went. `utils/fusionSplit.js` states the rule. `characterAggregation.js` applies it inline (Phase 3); every other aggregation calls `computeMatchFusionDeltas()` once per match and `applyFusionSplit()` on each character's `extractStats()`. **A split stays on its side of the match**: deltas are keyed `side:originalFormId`, and Phase 3 adjusts this file's row on the fusion's own side (`rowOf`), because a team's test against itself fields the same character on both sides. The split carries the per-slot skill counts and the fighting-style hits too; before 2026-09-28 it moved battle time without the hits, which skewed both partners' per-minute rates.
  - **A partner the file leaves out still takes its half** (fixed 2026-09-30). The AI always fuses with a partner still on the bench, and the game writes that partner a record (no battle time, `bFusionPotara: true`) only two times in three: 12 of the 32 fusions in the corpus have none, 11 of them Goku Black → Fused Zamasu, and the split used to be skipped there, the initiator keeping the whole fusion. **Every reader of a match's characterRecord goes through `withAbsorbedPartners()`** (`utils/fusionSplit.js`): the four aggregations and `matchRecord.js`'s `battleDataOf()`. It adds the record the game would have written, with no capsules or AI (`unrecorded`) and no lineup slot: its key names the side but holds no member number (`isAbsorbedKey`), so **every count of a lineup's slots must skip it**, or the last real member stops being the Anchor. Match rows carry `absorbed` (the game's flag, recorded or not) and `unrecorded`. An unrecorded partner is in the roster, the leaderboard, Performances and the Match page (last, "Fused in", "Build not recorded"), but not in a lineup strip (`matchSummary`, `teamLineups`), a position, or a build (`characterBuilds` skips it). `verify-team-page` checks every fusion is split, its partner recorded or not.

## Transformations (`src/utils/transformation.js`)

How often a character transforms, and which AI strategy and capsules get it to, came back after the redesign dropped it (settled with the league on 2026-09-30; the plan's "Transformations" section has the measurements and the four steps). **Every page reads a transformation through this module**, never from `formChangeCount` directly:
- **A transformation is any form change the character makes itself, fusions included**: the AI treats them as one behaviour, both spending the skill gauge. A fusion counts for the character that starts it (its record holds it); form changes after a fusion are the fusion's.
- **The rate is over counted matches**: fought, not fused in from the bench by a teammate (`m.absorbed`: it never fought as itself), no Broly's Ring (`BROLYS_RING`, which blocks transforming), and for a character that can only fuse, its partner on its team (`lineupIndex(rows, charIdFor)`). A match it transformed in always counts. The lineup check is as good as the file: a teammate that never entered often has no record, so a fusion-only character's match whose partner sat out the whole match is left out with the ones where it was not fielded.
- **Reverts are not transformations.** `transformations.json` lists the move back to a family's base beside the moves up; `isRevert()` sets it aside (the base is the form whose name the other contains, else the family's hub), so a form whose only move is down cannot transform. No match file has ever recorded a revert, and `verify-transformations` warns if one does.
- **"Default" is not an AI strategy** (`UNKNOWN_AI`): files whose AI was lost to a since-fixed bug that transforming set off. They count for the character, never in an AI comparison.
- `transformationSummary(matches, { id, lineups })` gives `{ able, matches, transformed, fused, rate, seconds, timed, left }` over any set of one character's matches; `seconds` is the median time on the field before the first transformation.
- `SKILL_GAUGE_CAPSULES` lists the capsules that act on the gauge (Super Transformation, Secret Measures, Dragon Spirit, Dragon Heart). League-wide none moves the rate past the noise unrelated capsules show, so they are compared per character.
- `fusionPartnerIds(id)` names the forms a character's fusion partners are listed as, and `onlyFuses(id)` says when it has no transformation of its own (Goku Black Super Saiyan Rosé, Zamasu, Vegeta (GT) Super Saiyan 4). **A fusion counts for the character that starts it**, so a partner that is always fused in reads 0%: Zamasu, 0 of 74 counted matches on the last two seasons, Ultra, every one of its fusions started by Goku Black, its "fused in from the bench" matches left out.
- `transformCount(m)` is how many transformations one match row holds (its own form changes up to and including a fusion; 0 for a partner fused in from the bench): the Performances table's count. `canTransformOrFuse(id)` is the reference's answer alone.
- **Capsules are compared on the same AI strategy** (`heldComparison(items, minOther)`: per group, counted matches with it against those without, `minOther`+ of them, weighted by the matches with it), by AI for one character (the Character page) and by character and AI pooled (Meta's Capsules detail). The AI moves the rate far more than any capsule, and teams pair capsules with particular AIs: an ungrouped with/without was off by 21 points on average. **`CAPSULE_NOISE` (10 points)** is where colour starts: measured 2026-10-01, the 33 capsules with Medium+ data moved the rate by a median 5.8 points, 80% within 10.5, the biggest moves by capsules unrelated to transforming (Ki Blast Attack Boost 3 −28, Style of the Strong +16); the gauge capsules sit inside it (Super Transformation −4, Secret Measures +6, Dragon Spirit +6, last two seasons, Ultra).

## Routing (read before adding a page)

`src/routes.js` is the **single definition of the URL scheme** and is now load-bearing: `main.jsx` builds its `<Route>` entries from it, and `App.jsx` derives which view to render from the pathname via `viewForPath()`.

- **`viewType` is not state any more — it comes from the URL.** `setViewType` was kept with the same name and signature but now navigates, so the existing call sites and the view dropdowns were untouched while every view became linkable, refreshable and shareable. Don't reintroduce a `useState` for it.
- **The routes, since the shell rebuild (2026-09-28):**
  - `/` is Home (view `home`).
  - `/characters` is the Characters page.
  - `/matches` is the Matches list and **`/matches/:matchParam` the Match page** (view `matches`). The param is the match file's name as a slug, or its path as an alias, rewritten to the slug with `replace: true`. See "The Matches list and the Match page".
  - `/teams` is the Teams table and **`/teams/:teamParam` the Team page**. The param resolves by team slug (or the raw tag, for hand-typed links) and is rewritten to the slug with `replace: true`, as a character's is.
  - `/meta` as before. **`/tables` redirects to `/characters`** (`REDIRECTS` in `routes.js`, a `<Navigate>` in `main.jsx` that keeps the query string): the Data Tables page was removed on 2026-09-29.
  - **`/sandbox/...` is the Sandbox**: the same views over uploaded files. `pathForView(view, { sandbox: true })` and `isSandboxPath()` handle the prefix, and a Sandbox path's fallback is its landing view (`matches`, the list of uploads). An upload's Match page is `/sandbox/matches/<slug>`, read from the `*` splat.
- App still renders every view itself, apart from the Character, Characters, Home, Meta, Teams, Team, Matches and Match pages. These routes make that switch addressable; splitting the remaining views into per-route pages happens in Phases 4–6 and **does not change the paths**.
- **The trailing `path="*"` catch-all is deliberate.** An unknown or stale URL renders the app rather than a blank page, which matters because links to this app get pasted into Discord and outlive whatever scheme was current when they were posted.
- **`/characters/:charParam` canonicalises.** A raw id is accepted forever, but if that character has a slug the URL is rewritten to it with `replace: true`, so what a viewer copies out of the address bar is the legible form. See "Character URLs are name slugs" below.
- **`npm run verify-routes`** (`scripts/verify-routes.mjs`, in `prebuild`) asserts every view round-trips through its path, in the league and in the Sandbox. It also checks that a prefix like `/charactersomething` or `/sandboxes` is not mistaken for its section, that malformed input falls back to Home instead of throwing, and that a match link, a slug or the path alias with its spaces and slashes, encodes to a **single** URL segment. A mistake here does not crash; it quietly shows the wrong view.

## The Matches list and the Match page

Built 2026-09-29 to the plan's "Page-by-page review". They replaced the single-match viewer (about 700 lines of nested cards in `App.jsx`) and the file tree.

- **A match's URL is its file name as a slug**: `Seasons/Season 0/S0 Week 3 Match 5.json` is `/matches/s0-week-3-match-5` (`utils/matchSlug.js`: `matchSlug`, `buildMatchSlugIndex`, `matchUrlKey`, `resolveMatchParam`). File names already say the season, week and match, or the team and test. The slug resolves against **every** match path (`br-data-tags.json`, which the scope already loads), not the scope, so a match link works whatever the scope bar says. The path is a permanent alias, rewritten to the slug. **`verify-match-slugs`** (in prebuild) fails the build if two files share a slug; all 2,505 are unique. Do not change `matchSlug()` without re-running it: that rots every shared link.
- **`utils/matchRecord.js` reads a match file once for every match view.** `battleDataOf()` finds the battle data in any of the file shapes the old viewer handled. `matchSummary()` is the list's cheap read (teams, winner, map, each lineup by slot, no stats). `readMatch()` is the Match page's: every character's `extractStats()` **with the fusion rule applied** (`applyFusionSplit`), its score for the match (`calculateMatchPerformanceScore`, the overall score's formula at one match), its position, and team totals. Side 1 is the file's first team, and `battleWinLose` is side 1's result.
- **`pages/MatchesPage.jsx`** (`/matches`): every match in scope, newest first (`compareMatchTime`), as `matches/MatchList.jsx` rows. Each side is its own line (result, logo, team, then its lineup, Starter first, in a strip as wide as the bigger side, so slots line up), then size, difficulty and map on a desktop. The whole row opens the Match page. The control row holds a search (match, either team, any character, the map), the count and the page's own switch, **Matches | Performances** (`view=performances`; leaving it drops the Performances params). 25 rows, then "Show more".
- **Performances** (`matches/Performances.jsx`, rebuilt 2026-09-29 on `shell/StatTable.jsx`; it was the old 60-column `DataTable`): one row per character per match in scope, for power users. `matches/performanceRows.js` (no React) builds the rows from the character aggregation's match rows, so every figure is the Character/Team/Match pages' own, fusion split included; the score is the match's own (`calculateMatchPerformanceScore`), as a tier pill. `verify-match-page` checks all 11,028 rows against `readMatch()`.
  - **Filters are the scope bar's**: the scope, then this view's chips after the divider (`matches/performanceChips.jsx`): Character (`char`, name slugs), Played for (`for`, team slugs: the team the character was on, where the scope's Team chip picks matches), Position (`pos`), Result (`res=won|lost`). The search (character, team, opponent, match, map, build, AI) is in the control row and not in the URL.
  - **A Columns switch** (`cols`) shows one group of figures at a time, the Match page detail's: Combat (default), Moves, Attack, Defense, Mechanics, Build. It keeps the table one screen wide instead of 60 columns. Switching group drops a sort on a column the new group lacks. Moves show "hit/thrown" and sort and colour by hit rate (ties to more hits; a match that never threw it is "–" and sorts last).
  - **The Build group's Forms column leads with the match's transformation count** (`transforms`, `utils/transformation.js` `transformCount()`: its own form changes, a fusion included, none after it) before the path, and sorts by it (`sort=forms`, the `forms` entry in `PERF_STATS`, which the column takes over in the Build group and a compact table can pick as "Trans"). Checked in `verify-match-page`.
  - **Three layouts**: ≥1180px has #, Character (team · position under the name), Match ("vs" opponent · map under it), W/L, Score, then the group; 900–1179px folds the match and result into the character's second line; below 900px the switch gives way to picked columns, two on a phone and four on a tablet, as the Characters table has (`shell/usePickedColumns.js`, stored per viewer).
  - Colours are placed among the rows the chips leave, not the search's, so one character's filter shows its best and worst matches. Default sort is newest match first (`sort`, `dir` in the URL).
  - **A row opens the Match page on that character**: `?open=<character slug>` (plus `&side=1|2` when both teams fielded it, `openParams()`), which opens its row and scrolls to it. Any link can use it.
  - The old table's own export went; the scope bar's workbook has the same data (Match Details sheet).
- **`pages/MatchPage.jsx`** (`/matches/<slug>`): the header (the match's name, both teams with W/L and links to their Team pages, Share, a back button), then Season, Phase, Type, Size, Map and Difficulty as label-over-value figures (`components/HeaderFigure.jsx`, shared with the Character page header). Then **a table per team** (`match/MatchTeamTable.jsx`): a header with the team's result and totals (damage, taken, HP kept, KOs), and a row per character in lineup order: position, portrait and name (a link to its Character page), build pill and cost bar, damage, taken, HP left, and the score as a `TierScorePill`. A phone keeps character, damage, HP % and score, and wraps long names. **Each team's header is tinted in its result's colour** (green won, red lost; `tint` and `RESULT_COLORS` in `utils/overviewPalette.js`, as the tier list tints its rows).
  - **A row opens `match/CharacterDetail.jsx`** (redesigned 2026-09-29; the first cut was a wall of 26 equal label/value pairs), built from the Character page Overview's pieces, **and boxed as the Overview boxes them** (the league asked for the borders back after a flat first try: they make each part easier to tell apart), so a match reads like a character's page for one fight:
    1. **The five headline figures** (damage dealt and taken, efficiency, damage/sec, battle time) as the Overview's tile grid, each on its `MedianTrack`, **placed in the per-match reference** (`perMatch` above), green or red only in the top or bottom fifth of single matches, with "League" (the typical match) under it. No rank text: a place among thousands of performances is not a leaderboard.
    2. **The moves** as the Overview's cards: Super 1, Super 2 and the ultimate as hit/thrown with its hit-rate `Ring` (the tick is the league's median rate), and ki blasts and both skills as its `VolumeCircle` (exported from `overview/Headline.jsx`). A match's own rate is never dimmed as a thin sample.
    3. **Attack, Defense and Mechanics** as short label/value lists (zeros muted), and the build as the one-column capsule list with its cost bar, each in its own box. A wide screen (≥1024px) runs the build down the right beside the counts and forms; below that the four sit two by two; a phone pairs only Attack and Defense.
    4. **Forms** (`components/FormBreakdown.jsx`, when it transformed): a timeline of how long it spent in each form, the forms, and, behind a **"Show figures" toggle that starts closed**, **one column per form** with a row per figure (time, damage, taken, efficiency, damage/sec, supers and ultimate as "#/#", ki blasts, skills, KOs, HP left), so reading across compares the forms. A row that is zero in every form is left out. **Every form stays in view** (the league, 2026-10-01): it is laid out by its own width (`useElementWidth()` in `shell/useMediaQuery.js`), not the screen's, and the forms share it, so a fourth form no longer scrolls out of a narrow detail panel. A form is named without the part every form's name shares (`shortFormNames()`: "Frieza (Z) 4th Form" is "4th Form", "Vegeta (Super) Super Saiyan God" is "Super Saiyan God"; the page or row already names the character), with the portrait beside the name when each form has 180px+, over it below that, and under 100px in the community's short forms (SSGSS, SSG, SS2, UI); the full name is in the tooltip. A timeline label that would run into the one before it, or the end's, is left out. **The forms' colours** (`SHADES`): white for the starting form, then purple, darker with each later form, spread over however many forms there are (two forms: white, purple 500; three: white, 400, 600; four: white, 300, 500, 700; five: white, 200, 400, 600, 800), so the steps stay far apart and the darkest still shows on the navy panel. By form rather than position (a form taken twice keeps its colour); none is the ranks' green and red or the picked form's orange. The league's call, 2026-10-01, after grey steps (too alike), unrelated hues (too loud) and pale blues (too close to the panel). **A fused form's column is the fusion's whole output, settled by the league on 2026-09-29** as the better account of how the match went; the character's own totals take half (the fusion rule), and the column says "Fusion with <partner>". A form that ended in a fusion shows no HP: the file's snapshot there holds the fusion's starting HP, more than the form's own maximum. `utils/formBreakdown.js` (`matchForms()`) shapes the data; the **Character page's Transformations tab passes averages into the same component** (`averageForms()`, 2026-09-29; `PerFormStatsDisplay.jsx` is gone).
  - **Picking a form filters the detail to it** (2026-09-29, the league's request). Each form in the forms box is a button; the picked one's swatch, frame and timeline segment turn the accent orange, and the tiles, moves and counts above show that form alone, under a **"Showing one form"** strip (`components/FilterStrip.jsx`, which the Character page's "Showing one build" strip now uses too) with "Show all forms", and the tile grid's frame turns orange. Rates (efficiency, damage/sec, hit rates) keep their league comparison; amounts (damage dealt and taken, battle time, ki blasts, skills) become the form's **share of all its forms**, since part of a match cannot be placed among whole matches. `matchForms()` gives each form a `stats` object under `extractStats()`'s names for this, every count being the difference between the snapshots either side of the form. **The best combo is a running maximum, not a count**: a later form's is known only when it set a new best, otherwise "–".
  - **Per-form figures are left out when both sides share the snapshots** (`sharedFormSnapshots()`, `readMatch()`'s `formSnapshotShared`). `characterIdRecord` is keyed by character id alone, so when both teams field the same character and it transforms on both (a team's test against itself), the file keeps one snapshot for the two, and one side's forms would be built from the other fighter's numbers. Their damage still adds up (the last form is the total minus the snapshot), which is why only the best-combo check caught it. 16 records in 8 matches, all tests; none is a fusion, so the fusion split is unaffected today. The Character page's Transformations tab leaves them out too (its per-match `forms` come from `matchForms()`). The older per-form aggregation (`formStatsArray` on character rows, `formStats` on a team's), which did not, was deleted on 2026-09-30: only the workbook's form count read it, as a fallback. Match rows now carry `formIds` for the workbook's form list.
  - **`utils/formStatsCalculator.js` read five counters under names no match file has** (`zCounterCount`, `lightningAttackCount`, `vanishingAttackCount`, `dragonHomingCount`, `speedImpactWins`), so per-form Z-counters, lightning and vanishing attacks, dragon homing and speed-impact wins were always 0, on the Character page's Forms tab too. Fixed 2026-09-29 to battleNumCount's own keys, the ones `extractStats()` reads.
  - The page fetches the full file (`BR_Data/<path>`, one request), because the corpus shards are trimmed.
- **Opening a match anywhere goes to its page.** App's `handleNavigateToMatch(path)` (a Team page's lineups and matches, a character's recent matches, the Performances table) navigates to `matchLinkFor(path)`, which carries the scope. The back button names where you came from ("Budokai", "Matches"), as on the other detail pages.
- **The Sandbox has the list, Match and Character pages over the uploads**: `/sandbox` is the list of them, `/sandbox/matches/<slug>` one upload and `/sandbox/characters/<slug>` one character over all the uploads (2026-09-30), with no Share, since uploads are not stored. One uploaded file opens straight on its page. App reads the character slug from the Sandbox splat (`charParam`), and `charPath()` puts the `/sandbox` prefix on every character link and the canonical-slug redirect there. The Character page's Performances link is off in the Sandbox, whose chips are hidden (a `char=` filter would be invisible).
- **The Sandbox's head is `pages/sandbox/SandboxPanel.jsx`** (2026-09-29): one flat panel, a drop zone while empty, then the uploads as rows (a readable one links to its Match page, a broken one says "Not a battle-result file", each removable), Clear and Add files, and the Sandbox's views (Matches · Characters · Teams · Meta) as underline tabs at its foot, links through `pathForView(view, { sandbox: true })`. Files can be dropped anywhere on the panel. **Uploads join the set** (App's `processFiles`); a file of the same name replaces its old copy. It replaced the old card, a collapsible green/red file list and a four-card "View Type" radio grid.
- **`matches/MatchList.jsx` sizes its Teams column to its widest line**: the lineup strip cannot shrink, and a column that could let it spill over Size and Difficulty at in-between widths. Below 1024px the size, difficulty and map move under the match's name.
- **`npm run verify-match-page`** checks, over the default scope and everything, that every match is listed once and newest first, and that the Match page agrees with the character aggregation (the Character and Team pages' source) on every slot's character, every side's result, and every character's damage, taken and HP, fusions included (11,028 rows). Over the raw files it checks the forms: each form once and in order, the forms adding up to the character's whole damage, taken and KOs, the five per-form counters matching the file's, and no HP on a form that ended in a fusion. And it checks the per-match reference places values correctly, and the Performances view: one row per character per match, each the Match page's character (name, position, result, score, damage), each `?open=` link opening exactly its own row, and the chips, sort and search. Not in prebuild.

## Shared presentational components (read before building any page)

**Tablets** (the league's ask, 2026-09-30): between 640px and about 1,100px the Characters, Teams and Team page tables were wider than the screen, so the page scrolled sideways. Now **every wide table has a size, from `useTableSize(fullFrom)`** (`shell/useMediaQuery.js`): 'phone' below 640px, 'tablet' from there until its full layout fits, 'full' after. A tablet draws the **phone layout with four stat columns** instead of two (`PICKED_COLUMNS`, widths from `pickedWidth`). Tables with pickers keep one list of four per viewer (`usePickedColumns`): a phone shows the first two, a tablet all four, so a pick carries across; an older two-key save is filled from the defaults, and picking a column another slot holds swaps the two. Tables with fixed figures (Teams, the Team page's Opponents and Roster) list a tablet's four themselves. Where each table's full layout starts, measured so none overflows: Characters Stats 1080px, Styles 1000px, Teams 1080px, the Team page's Roster and Opponents 940px, Usage, a character's Matches, Performances and Meta's AI strategies and Capsules 900px (AI strategies 100px more per action column), and the Builds tables 820px (they switch to their phone rows below it; no pickers). A new wide table picks its own `fullFrom` the same way: measure where it stops overflowing.

**Every table is `shell/StatTable.jsx`** (since 2026-09-29; the league wants every remaining table on this one template, and the old styling and setup gone by the end of the restyle). It takes a list of columns (`key`, `label`/`short`, `width`, `align`, and either a stat's `get`/`fmt`/`text`/`dir` or a `cell(row, i)`), draws the panel, the sticky header under the scope bar, sortable heads, 46px rows that link or open, stat cells (white number over a bar, green/red only in the top/bottom fifth of `pool`), and "Show more". `RANK_COLUMN` is the "#" column; `selected` and `expanded`/`renderExpanded` give layout A's picked row and its detail under the row (`meta/PooledTab.jsx` puts that detail in a side panel on wide screens). `placements()` (in `pages/characters/characterRows.js`, binary search, nulls left out) does the colouring. A table too wide for a phone picks two columns with `shell/usePickedColumns.js` (`usePickedColumns`, `pickerChip`), as Characters and Performances do. Since 2026-09-30 every stat table is on it, the Characters, Teams, Team page Roster and Opponents and the Builds tables too (they drew the same look by hand, and were its model); `rowTitle(row)` gives a row a tooltip, and a column's `title` is its header's tooltip, sortable or not (`SortHead` dropped it until 2026-10-01, so no sortable header had shown one). A page's filters are scope-bar chips and its search sits in the page's control row, never a settings panel inside the table.

`StatBar`, `PerformanceIndicator`, `PerformanceScoreBadge`, `StatGroup`, `MetricDisplay`, `BlastMetricDisplay`, `BattleTimeVariance`, `BuildYamlButtons`, `BuildTypeTooltipWrapper`, `BuildTableView`, `BuildDisplay` and `MetaAnalysisContent` were all defined **inside `App.jsx`**, which meant they were unreachable from anywhere else. The first Character page reinvented the build display as a result, and shipped a worse version of something that already existed. They now live in:

- **`src/components/stats/`** — the stat primitives. Deleted on 2026-09-29: nothing had imported them since the pages were rebuilt. The score pill every table shows is `components/TierScorePill.jsx`, which `smoke-character-page` now checks.
- **`src/components/build/`** — now only `BuildYamlButtons.jsx` (Copy YAML / Download, restyled to the shell's buttons) and `buildYaml.js` (`generateBuildYaml`, `useCopyFeedback`). `BuildTypeTooltipWrapper`, `BuildDisplay`, `BuildTableView` and the barrel were deleted on 2026-09-29, when the Character page's Builds tab moved onto Meta's Builds table.
- `MetaAnalysisContent` was deleted on 2026-09-28, when `pages/MetaPage.jsx` put its two analyses behind tabs.

**A build shows as `BuildPill` (`character/overview/BuildPicker.jsx`) with `CostBar` and the one-column `CapsuleList` (`meta/BuildsTable.jsx`)**, never as capsules spread across columns. A pill takes its **main type's** colour, the type before the slash (`buildTypeColor`: "Defense/Blast" is Defense's blue; it used to match names in a fixed order, so Blast won), and **Balanced Hybrid a light slate** (`HYBRID_COLOR`), no type's hue: it was Skill's purple and read as a Skill build (both the league, 2026-09-30). The workbook's build column follows the same rules. Note `buildComposition` is an object — `.label` is the display string.

The bodies moved **verbatim**; the only edit to any moved line was an `export ` prefix. Two things worth knowing about that move:

- **`parseCapsules` was deleted**, not moved — it was defined and never called.
- **`npm run smoke-character-page`** (`scripts/smoke-character-page.mjs`) renders the character page through `react-dom/server` against real corpus rows, across every layout, and prints a stack trace when it throws. `verify-character-page` checks the DATA contract and cannot catch a render bug; those surface in the browser as a **blank white page** with the real error buried in the console. It loads app modules through Vite’s SSR pipeline so aliases and `?raw` imports resolve as they do in a build, but imports React, react-dom and react-router **natively** — they are CommonJS, which Vite’s SSR runner cannot evaluate.
- **`React` is deliberately not whitelisted** in `verify-self-contained`. The automatic JSX runtime means JSX never names the identifier, but an explicit `React.useState(...)` or `React.Fragment` still needs the import. Whitelisting it once made that checker blind to exactly its own bug class: `useCopyFeedback` moved out of `App.jsx` still calling `React.useState`, which blanked both the character page and any expanded leaderboard row.
- **`npm run verify-self-contained`** (`scripts/verify-self-contained.mjs`, in `prebuild`) parses every file under `src/components/`, `src/pages/` and `src/shell/` and reports any identifier it references but does not import. This exists because **a Vite build does not catch that class of mistake**: a component that used to reach something `App.jsx` imported becomes a runtime `ReferenceError` on whichever path touches it, so a rarely expanded panel could stay broken indefinitely. It globs rather than reading a list, so it cannot fall behind as Phases 4–6 move more components out.

## The Character page (`src/pages/CharacterPage.jsx`)

The first real page of the redesign, behind `/characters/<name-slug>`.

- **It computes nothing of its own.** The Usage, Builds, Transformations and Matches tabs read an aggregated row that `characterAggregation.js` already computed, through the shared row builders (`filterAggregatedData`, `leagueBuilds`, `averageForms`, `transformationSummary`, `performanceRows`). The Overview works from that row's per-match rows through `src/utils/characterOverview.js`, the same code that builds the league reference. A wrong stat is an upstream bug.
- **`App.jsx` renders it in place of the Characters page** when `deepLinkedCharacter` resolves; `CharactersPage` is gated on `!deepLinkedCharacter`. App still owns data loading, so the page takes everything as props.
- **Three files**: `CharacterPage.jsx` owns the four states and nothing else, `character/CharacterBlocks.jsx` holds the content with no opinion about arrangement, and `character/CharacterTabs.jsx` arranges it. **Tabs were chosen** over a dense single column and a sticky-rail variant, which were built alongside and compared with real data — tabs won on navigation and, more importantly, on extensibility: a new kind of analysis becomes a new tab rather than another band competing for space. `TABS` in that file is a plain registry; adding one means a row there and a case in the panel switch. The tabs are Overview, Usage, Builds, Forms and Matches. **Since 2026-09-29 the four after Overview are on the one table template** (`CharacterBlocks.jsx` keeps only the header, `IdentityBlock`):
  - **Usage** (`CharacterUsage.jsx`): the usual team, position, AI and map as header figures, then **By position** and **By team** as `StatTable`s with the Characters table's own columns (`CHAR_STATS`, win % last), each row the leaderboard filter's recomputation of that cut (`filterAggregatedData` on the matches at that position / for that team). **A row toggles its cut**: a position `pos=`, a team `for=` (see "The page's cuts" below).
  - **Builds** (`CharacterBuilds.jsx`; a **Trans %** column, between Score and Win %, for a character that can transform or fuse: each build's counted matches it transformed or fused in, `transformRows.js` `transformByBuild()` by build code, dimmed under 5 counted matches, sortable; on a phone it takes Eff's place, since four figures left the build too little room; `BuildsTable`'s `transform`): Meta's Builds table (`meta/BuildsTable.jsx`, `showCharacter={false}`, `pickFirst={false}`) over `leagueBuilds([character])`, most used first. **A row toggles `?build=`** and shows its capsules beside the table (under the row when narrower); nothing is picked until then, so the highlighted row is always the page's cut. Copy YAML / Download (`components/build/BuildYamlButtons.jsx`, the Match Builder's format) sit under every capsule list, on Meta too.
  - **Transformations** (`CharacterTransformations.jsx`, the plan's "Transformations" step 3, 2026-10-01; the Forms tab until then, and `?tab=forms` still opens it): for every character that can transform or fuse (`transformationSummary().able`: from the reference, or because it did, whether or not it did in this scope). Every count is `utils/transformation.js`'s (see "Transformations" above), over the page's row under every cut but the form. The header figures: **Transformed** (rate, x of N counted), **First transformation** (the median time on the field before it) and **Fused** for a character that can fuse; a character that can only fuse gets one figure, **Fused**, and a line naming its partner (`fusionPartnerIds`, `onlyFuses`), saying so when the partner was never on its team. A line says which matches were left out and why. Then three parts, **each full width** (the league, 2026-10-01: beside each other, the shorter of the AI table and the capsules left a gap, and in a narrower column the forms' fixed 210px columns cut off a fourth form):
    - **By AI strategy**, a `StatTable` (`transformRows.js` `transformByAI()`): Matches (counted), Transformed %, First (lower is better, so it colours the other way), sortable as local state, Transformed % first. A row under `THIN` (5) counted matches is faded and **listed after the rest** (a 1-of-1 is not the strategy to pick); when every row is, nothing fades and the footnote says so. Default has no row; its counted matches are in the header and a footnote line. **A row opens Meta › AI strategies on this character with that strategy open** (App's `aiLinkFor`: `tab=ai&char=<slug>&sort=transform&open=<strategy slug>`, the scope kept; none in the Sandbox).
    - **Skill gauge capsules** (`gaugeCapsules()`), a card each, four across on a wide screen, two on a tablet, one on a phone: Super Transformation, Secret Measures, Dragon Spirit and Dragon Heart, each **with and without on the same AI strategy** (per AI, its matches with it against its matches there without it, `MIN_OTHER`+ of those, weighted by the matches with it), the rate and the first transformation's time, coloured from `CAPSULE_NOISE` (10 points), dimmed under `THIN` compared matches. Held by AI because the AI moves the rate far more than any of these capsules and teams pair them with particular AIs: a plain with/without differed by 21 points on average over 40 character-capsule pairs (last two seasons, Ultra, 2026-10-01). Broly's Ring is a line under it: how many matches carried it, which the figures leave out.
    - **The Widen link** (`shell/useWidenLink.jsx`, shared with Meta's AI strategies) when there is too little to pick an AI by: under two strategies with `THIN`+ matches, most rows thin, or under 30 counted matches.
    - Then its **forms** (`CharacterForms.jsx`): `FormBreakdown` fed `averageForms(matches)` (`utils/formBreakdown.js`): each form's figures averaged over the matches that reached it, from the `forms` the aggregation now stores on each match row (`matchForms()`, the Match page's own reading, so the two agree; shared-snapshot and snapshot-less records are left out and counted). The figures start open, and a "Reached" row appears only when some form is reached less often than the rest. The form every match began in says "Starting form" there instead of a count (`averageForms`' `start`): it is where the character starts, not a form it reached. The tab shows when any match in view transformed. **A form is a button that cuts the page to it** (`form=`, below).
  - **Matches** (`CharacterMatches.jsx`): the Performances table without its Character column (`performanceColumns({ withCharacter: false })`): every match in view, the Columns switch and sort as local state, a row opening the Match page on this character (`matchLinkFor`), and "Open in Performances ↗" (`performancesLink`, keeping `for=`).
- **The header leads with the character's portrait** (80px, like a Team page's logo; the 192px cut keeps it sharp), then the name and, under it, **four equal figures: Tier, Score, Rank, Matches**, each a small label over its value like the Overview tiles (`IdentityBlock` and `HeaderFigure` in `CharacterBlocks.jsx`). The tier is its plate, and the score keeps its tier pill, so a Z score still breathes. On a phone the portrait (56px) and name share a row and the four figures run under them, full width. Chosen on 2026-09-29 over a badge row and a plate docked on the portrait. App passes `portraitId`, the id the URL resolved to.
- **The Overview tab lives in `character/overview/`** and implements the approved design (plan: "Overview tab: approved design"):
  - `OverviewTab.jsx` places the view against `src/config/style-baseline.json`.
  - `Headline.jsx` holds the five tiles and six move cards.
  - `StyleBand.jsx` holds the fighting style, build, AI and the Radar / Bars "How it fights". **A phone gets its own Bars layout** (`PhoneStyleBars`, 2026-09-30): each style is a block, its name, rate ("20.1/min · league 22.3") and rank on one line and its bar the full width under them, and the sub-figures (Rush and Heavy, the supers, the skills, Defense's four) two to a line under it, each its name and value over a half-width bar. The desktop row, four figure columns beside the bar, left the bar a stub on a phone and the sub-figures ran off the screen.

  - `parts.jsx` has the rank text, score pill, `Tip` / `TipTable` (floating-ui Me / League tooltips) and `MedianTrack`.
  - Colours come from `src/utils/overviewPalette.js`: style colours, and rank colour for the top and bottom fifth only.

- **One build at a time, via `?build=<code>`.** `overview/characterBuilds.js` lists a character's builds (key, short code, label, AI, capsules, score). Each build's `row` is `filterAggregatedData([character], { activeBuildFilters: { [name]: key }, charMap })`, the leaderboard's own build filter. `CharacterTabs` resolves the code with `findBuildByCode`. An unknown code (another character's) is ignored. `App.jsx`'s `scopeSearch` strips `build`, `for`, `form` and, on a character's page, `pos` (and the Team page's `vs`) from the query string on the way to the leaderboard, other views or another character; `charMap` is passed down for form names on a filtered row.
- **The page's cuts** (2026-09-29, the league's review): a build (`build=`), a position (`pos=1|2|3`) and a team (`for=`) each cut the whole page, identity, Overview, Usage, Transformations and Matches, and **each is set by clicking the thing it keeps and cleared by clicking it again**: a Builds tab row or the Overview's build picker, a Usage position row, a Usage team row (or the scope bar's Played for chip). `character/characterCuts.js` has `readCharacterCuts(params)` and `cutCharacter(row, { pos, build, team }, charMap)`, the leaderboard's filter over just those matches (null when none pass).
  - **Each list keeps all its own options while cut**, computed under every other cut: the Builds tab lists the builds at the picked position, By position every position with the picked build, By team every team under both. The team is applied upstream by App (it also sets what the rank is counted among), so App passes `teamsRow`, the same character over every team, while `for=` is set.
  - **Every cut shows as its own strip above the tabs** (`components/FilterStrip.jsx`): "Showing one build", "Showing one position", "Showing one form", "Playing for", each with its match count and its own clear. The leaderboard rank goes while a build, position or form is cut (the leaderboard ranks characters); a team keeps it.
  - **A form (`form=<form name slug>`, a form on the Transformations tab) follows the Match page's rule** (the league's choice, 2026-09-30). The page keeps the matches that reached the form, and **the Overview shows the form's own figures** in each: `formSlices(matches, slug)` in `characterCuts.js` puts each match's form `stats` (from `matchForms()`, which the aggregation now keeps on its match rows' `forms`) in place of the match's, so `overviewFromMatches` reads them unchanged (a form taken twice adds up; a file without hit counts loses its hit fields). Rates keep the league comparison; amounts (damage dealt and taken, battle time, ki blasts, skills) show as the form's **share of all its forms** over those matches (`HeadlineTiles` / `MoveCards` `shares`). The tabs' tables list those matches whole, so their scores stay whole-match scores, and the header drops Tier and Score (`hideScore`): the score's damage and HP would read part of a match as a weak whole one. The Forms tab lists every form under the other cuts, the picked one orange (`FormBreakdown`'s `selected` / `onSelect`).
  - Cuts that leave no match (say a build never run at the picked position) show the strips and "No matches with all of these filters", with no figures, rather than silently falling back.
  - `verify-character-page` checks that a build cut equals the leaderboard build filter's row, that position cuts split a character's matches exactly, and that cuts combine.
- **The Characters table and tier list link in.** Every row and tile is a `<Link>` to the character's page. `characterLinkFor(name)` in `App.jsx` uses `charUrlKeyByName`: a name slug, or the raw id for a character missing from the CSV. It carries the scope params, so the page's numbers cover the same matches as the list.
- **The open tab is in the URL** (`?tab=usage|builds|transformations|matches`, none for Overview; the league, 2026-09-30), so "look at this character's builds" is a link. A tab the view has nothing for falls back to the first one. `TAB_ALIASES` keeps old names working (`forms` opens Transformations). App's `scopeSearch` drops `tab` on the way to another page. `smoke-character-page` checks it.
- **Rank comes from `performanceReference`, not `filteredAggregatedData`.** Same reasoning as the tiers: the population is defined by the filters that change *which matches count*, so "#12 of 107" means the same thing whatever the visitor has sorted or selected. The deep-link effect therefore **must not** set `selectedCharacters` — that would flatten the rank to #1 of 1.
- **Four states, and the differences matter:** loading, empty-scope, not-found, and rendered (`reason` prop). **Do not infer loading from an empty list** — that was a bug: a tag filter matching no files (`S1 + Season` is empty today, since every Season 1 file is tagged `Test`) leaves the list empty forever, and the spinner never resolved. App decides from the real signals: an empty scope (`scopeState.paths` is `[]`) is empty-scope, and a scope that is not `ready` or whose matches are still arriving (`dataLoading`) is loading.
- **The data scope is printed on the page**, built from the scope in the query string (`describeScope()` in `shell/scopeModel.js`) rather than from component state — so the page's description of its scope and the link someone pasted come from the same source and cannot disagree.
- **Watch for object-valued fields.** `topBuilds[].buildComposition` is an object (`{ primary, label, type, breakdown }`) whose display string is `.label`, and `equippedCapsules[]` entries are objects carrying their own `.name`/`.capsule.cost` — **not** ids to look up. Both render as `[object Object]` or throw if treated as strings. Note this **depends on `capsuleMap` being populated**: with an empty one, `buildComposition` comes back as the string `'No Build'`, which is why the verifier below feeds the real lookups.
- **`npm run verify-character-page`** (`scripts/verify-character-page.mjs`) is the guard, and it exists because this page **cannot crash on missing data** — it renders an em dash, or `NaN`, or silently drops a section. It **scrapes the `character.` / `viewRow.` / `allRow.` field reads out of the page source**, so the field list cannot drift from what ships. It then asserts:
  - each field exists on real rows, and headline stats are finite on every row
  - text-rendered fields are never objects
  - the `slug → id → name → row` join holds for every character in the corpus
  - every `m.<field>` the Overview reads exists on real match rows
  - build codes are unique per character
  - each build's filtered row has the build's match count
  - all six fighting styles place for every character

  Not in `prebuild` (it aggregates real shards, like `verify-filters`). Until 2026-09-28 its source glob tested `[\/]` for the path separator, which on Windows scanned only `Character*.jsx` files and skipped everything under `character/`.
- **`npm run smoke-character-page`** renders the page through Vite's SSR pipeline with real rows. It covers the Overview's content, the Bars view (via `StyleBand`'s `initialView` prop, since a server render cannot click), every other tab, a `?build=` link and an unknown code, `?tab=` links, and it fails on visible `NaN` / `undefined` / `null` text. It cannot see layout: the `App.css`-beats-Tailwind bugs described under "Styling" passed it. For layout, build, serve with `node scripts/serve-dist.js`, and screenshot with `npm run shot` (`scripts/dev/`).

## `<ShareButton>` (`src/components/ShareButton.jsx`)

Copies an **absolute** link to the current view — origin + `BASE_URL` + pathname + query, the same `BASE_URL` `main.jsx` gives `BrowserRouter` as its basename. Relative paths are useless in a Discord message, which is the entire point of the URL scheme.

It shares the live location by default, query string included, so a scoped or filtered view travels with the link. `navigator.clipboard` needs a secure context and is absent over plain-HTTP LAN testing, so there is an `execCommand` fallback. **Image-card export is not built yet** — that is the remaining piece of the share-snippet goal.

## Team positions: Starter / Middle / Anchor

The league calls the first slot the **Starter**, never "Lead". **`src/utils/positions.js` is the single source** for every user-facing position label: `POSITION_NAMES`, `positionSlot()` and `positionLabel()`. It imports nothing, so aggregation code and build scripts can use it.

- The raw data stores position as a **number** (`matches[].position` is 1/2/3), while `primaryPosition` is a **word**. Anything that displays a position must go through `positionLabel()`, or a table shows "1 / 2 / 3" — which shipped once on the Character page.
- The app used to mix both names: Position Analysis, its table and the Excel export said "Lead"; `characterAggregation.js` and the team panel said "Starter". All now read `POSITION_NAMES`.
- **Key colour maps and lookups on the slot number, not the word.** `preparePositionData()` emits the label and the Position column colour-coded rows by matching that same string, so renaming one side alone would have silently uncoloured the rows. That map is now keyed by `positionSlot(value)`.
- `positionSlot()` still accepts `"Lead"`, so anything carrying the old word resolves rather than breaking.
- The team panel's richer ordinal model for 4v4/5v5 ("Second (Middle)", …) is separate and intentional; only its slot-1 name comes from here.
- `smoke-character-page` asserts slot 1 renders as Starter and fails if it is renamed back.

Imports `characters.csv`/`capsules.csv` directly from `/referencedata/` at build time via Vite's `?raw` import, and `teams.json` (`src/utils/teams.js`) and `transformations.json` (`utils/transformation.js`, `fusionSplit.js`, `formBreakdown.js`) as JSON (see root `CLAUDE.md` — **edit those files at the repo root, never the local `referencedata/` copy that `vite.config.js`'s `copy-shared-referencedata` plugin writes here**, it's overwritten on every build). `src/config/capsule-rules.yaml` encodes capsule-restriction/build-legality rules.

## Gotchas

- `@szl/ui` (aliased in `vite.config.js`) provides the shared `NavBar` — see `packages/ui/CLAUDE.md`.
- No test suite. Validate changes by running `npm run dev:analyzer` and checking the relevant view in the browser; for BR_Data/tagging changes, confirm the generated `public/br-data-*.json` files actually changed after a build.
- **Count skill uses from `runBlastCount` (`EXA1` / `EXA2`), never from `battleNumCount.eXACount`.** The two agree in every Season 0 file (99–100%). In Season 1 files `eXACount` inflates: ~12× its Season 0 rate per minute on the field while every other `battleNumCount` counter stays within 0.7–1.4×, and it records the impossible — Panzy logs `eXACount: 10` in an 88-second match (`BR_Data/Tests/Tiny Terrors/OS1 Tiny Terrors Test 16 Match 1 R1.json`) when her skill points allow about 4 uses. `EXA1`/`EXA2` hold steady across seasons and match the match footage (checked by the league against a test video: 2 uses of Skill 1 where `EXA1: 2`). They also give the per-slot split. `extractStats.skillsUsed` is EXA1 + EXA2 since 2026-09-28; it used to be `eXACount`, which inflated the leaderboard's skill figures (12,761 uses across the data against 8,266 real ones).
- **There is no reliable ki-blast hit rate — do not build one from `attackHitCount`.** The ki-blast hit codes (`RSB`, `DRSB`, `JRB`, `JSBN`) credit a deflected *enemy* blast that lands to the deflector, as if it were their own hit. Confirmed against match footage (`BR_Data/Seasons/Season 0/PS0 Week 1 Match 3.json`: Bardock fired 3, 2 hit, and 3 enemy blasts bounced back into the opponent — the file records 5 hits from 3 fired). About half of all character-matches include deflections, so the true league rate sits anywhere between roughly 29% and 38%, and the error favours characters who deflect a lot. Use `shotEnergyBulletCount` (blasts fired) for ki-blast volume instead. `battleNumCount.reflectEnergyBulletCount` is **enemy blasts this character deflected** — it tracks the opponent's blasts fired (r = 0.77) and never exceeds them in any of 1,824 one-on-one pairings — but it is **not** a measure of defensive skill: characters auto-deflect while dragon dashing or in max power, so never weight it into a defensive rating.
- **What each `attackHitCount` move code means** (rush vs heavy melee, rush vs smash ki blasts, counters, movement, reactions), and how sure we are of each, is in **`docs/ACTION_CODES.md`**. Read it before building any stat on per-move hits.
